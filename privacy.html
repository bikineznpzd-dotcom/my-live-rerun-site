1. Who is responsible for the project

My Live Rerun Studio is developed by an individual developer in Thailand. No company name, street address, or telephone number is published. Privacy, legal, and general inquiries may be sent to bikineznpzd@gmail.com.

This policy covers this informational website and the current My Live Rerun Studio desktop source. No production Auth Broker is included in the project. TikTok, GitHub Pages, and any RTMP/RTMPS destination operate under their own privacy practices.

2. Data handled by this website

The website source contains no account system, contact form, analytics script, advertising SDK, or first-party cookie. Its JavaScript only controls mobile navigation and displays the current year.

If hosted on GitHub Pages, GitHub may process request data such as IP addresses and technical logs under GitHub's own policies. The final hosting arrangement and any future analytics must be reviewed before publication.

3. Data stored locally by the desktop application

The current source writes the following information beneath Electron's Windows user-data directory:

  • Five-channel settings, including channel names, account labels, output resolution, FPS, bitrate, encoder choice, overlay text and style, recovery settings, and destination mode.
  • Local file-system paths for videos added to each playlist.
  • Configured RTMP/RTMPS server URLs.
  • Generated FFmpeg concat playlist files containing local video paths.
  • Per-channel FFmpeg logs and a renderer diagnostic log.
  • Generated H.264 preview proxy files when a source cannot be previewed directly.

The video files selected by the user remain at their original locations. A compatible preview may be read directly; otherwise the application creates a local proxy in its preview cache.

4. Account connection data

The current desktop source contains client-side fields for a display name, avatar URL, Open ID, granted scopes, authorization method, expiry time, connection status, LIVE-permission status, destination metadata, and a configured server URL. Mock account data can be created for local development.

The desktop source does not store TikTok access tokens or refresh tokens directly. Its planned real-login flow expects a separately operated Auth Broker to exchange an authorization code and return an opaque session handle. The current project does not include that broker, so production token processing, retention, rotation, revocation, hosting, and subprocessors have not been implemented or verified.

If a session handle is returned in the future, or if the user manually enters an authorized Stream Key, the desktop client encrypts it with Electron `safeStorage`. If operating-system encryption is unavailable, the application refuses to store the secret.

5. When data can leave the device

Authentication

No production Auth Broker is included or configured by this website. If the planned desktop OAuth flow is configured later, the callback is designed to send a channel identifier, authorization code, PKCE code verifier, and redirect URI to the configured Auth Broker. The planned QR workflow would send a channel identifier, Client Key, requested scopes, and a broker request identifier.

Streaming

When streaming starts, FFmpeg reads the selected local media and sends encoded video and audio to the RTMP/RTMPS destination chosen by the user. Local test mode uses a loopback destination. If a user configures an external destination, the media leaves the device and is processed by that destination provider. TikTok LIVE streaming has not been verified.

Logs and support

Logs can contain file paths, codec details, process messages, destination host information, and other technical diagnostics. The displayed FFmpeg command attempts to redact a final Stream Key; however, raw diagnostics should still be treated as sensitive. General support, privacy, and legal inquiries may be sent to bikineznpzd@gmail.com. Sending diagnostic logs is optional; users should review and redact sensitive paths, host details, and credentials before including logs in an email.

6. Why the data is used

  • To restore channel configuration and playlists between application launches.
  • To preview and encode user-selected video.
  • To support account-connection development when the user explicitly starts it.
  • To send a stream to a destination explicitly configured by the user.
  • To diagnose playback, encoding, and connection failures.

The application is currently a personal development project, not a confirmed commercial service. Legal bases and additional notices must be reassessed before it is offered to other users.

7. Retention and deletion

No time-based retention limit is implemented. Channel settings and account-state files remain in Electron's user-data directory until overwritten or the application's user data is manually cleared. Per-channel and renderer logs are appended and remain until manually deleted. Generated concat files are overwritten per channel, while completed preview proxy files remain in the preview cache until manually removed.

The preview generator removes an incomplete temporary proxy after a failed conversion, but it does not automatically remove completed proxies. Disconnecting an account replaces that channel's local account record with a disconnected default and removes its locally stored encrypted session handle and Stream Key.

Because no production Auth Broker is implemented, server-side token retention, backups, deletion, and revocation behavior do not currently exist in this project.

8. Security

The desktop application uses Electron context isolation, disables Node integration in the renderer, limits local media access to files selected by the user, and uses operating-system-backed encryption for supported secrets. No system can guarantee absolute security. Users should protect their Windows account, TikTok account, local videos, and streaming credentials.

9. Your choices and data controls

Users can remove videos from a playlist, change local settings, disconnect an account, and manually clear the application's user-data directory. If real platform authorization is enabled in the future, users should also use the platform's official controls to review or revoke authorization.

Privacy inquiries may be sent to bikineznpzd@gmail.com. Requests remain subject to identity verification and rights available under applicable law.
